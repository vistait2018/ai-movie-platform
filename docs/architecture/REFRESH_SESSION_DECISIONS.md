## Chosen implementation

- Add auth_sessions and refresh_credentials; nullable indexed AccessGrant.session_id references a session with ON DELETE CASCADE. Existing grants remain NULL/legacy and work until their existing expiry/revocation. No fake refresh credential or automatic backfill is created for them.
- Preserve the exact default login JSON (existing tests assert its three keys). Opt in with session_mode=refresh on the existing login request; default session_mode=access. Refresh-mode login returns the existing access fields plus session_id, refresh_token and refresh_expires_in. Each login creates an independent device/session family. This is an explicit compatible contract, not a cookie adapter.
- Opaque refresh credentials use 48 random bytes, purpose-bound SHA-256 digests only, and unique digests. Keep consumed rows for replay detection. Proposed configurable defaults: refresh credential lifetime 7 days, absolute session lifetime 30 days; each child is bounded by the original session expiry. Access remains the existing configurable short lifetime and cannot exceed session expiry. No unbounded sliding family lifetime.
- Rotation locks User → AuthSession → RefreshCredential in that order. Password reset/logout-all take the same user lock. Exactly one successor per parent is enforced by a unique parent reference. Every successful refresh consumes its credential, revokes previous family access grants and atomically issues one new refresh/access pair.
- **Strict reuse policy, no grace window:** presenting any consumed credential revokes that session/family and every associated grant/refresh credential, including the just-issued successor after a concurrent race. A race may yield one 200 and one 401; after reuse commits, even the winning response's credentials are unusable. Network retry after a lost refresh response requires login again. Clients must serialize refresh calls; one family compromise does not revoke unrelated devices.
- Access checks continue consulting PostgreSQL and also check linked session expiry/revocation/ownership. Pending, suspended, deactivated and deleted users cannot refresh. Logout-all and password reset revoke all sessions and all legacy/new grants; reset never activates an account.
- POST /api/v1/auth/refresh uses JSON refresh_token, with no cookie fallback. POST /api/v1/auth/logout and /logout-all use access Bearer credentials. Logout revokes the current linked family (or only the legacy grant); repeated logout with the same still-unexpired signed credential is idempotent. An obsolete rotation-revoked access token cannot revoke a still-live successor family. Logout-all requires currently valid access and rechecks under the user lock. Expired access must be refreshed before logout, then local credentials discarded.
- Browser clients retain access in memory; do not persist refresh secrets in localStorage/sessionStorage. Until the next secure cookie/BFF + CSRF/origin increment, browser clients should keep the existing access-only mode or strictly ephemeral in-memory sessions. Flutter may hold access in memory and refresh in OS Keychain/Keystore-backed secure storage. No Flutter UI, cookies or CSRF bypass is implemented here.
- Fail closed on database/Redis/signing failures; generic 401/503 errors; configurable IP/token-digest throttling. Security audit records and structured events contain event names and UUID identifiers only, never credentials/headers/emails. Commit before returning credentials; transaction failures cannot consume/issue a partial chain.

## Verification and migration policy

Run official runner and existing quality/security checks; verify live service health and canonical GitHub jobs. Downgrade would discard session/refresh state and unlink still-stored grants; revoke all affected access first if rollback is ever explicitly authorized. No live downgrade is part of this task.

Reference: [RFC 9700 refresh-token rotation and replay detection](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14). This is first-party session authentication, not a claim to implement an OAuth authorization server. Remaining Phase 2 requirements include browser cookie/CSRF sessions, RBAC, MFA and production email/security acceptance.
